# Kaldrivon MiniSMO 0.7.1 — Release Notes

Windows 11 x64: `Kaldrivon-MiniSMO-0.7.1-Setup.exe` (checksum in `.sha256`), code-signed by Kaldrivon. Installs over 0.7.0, 0.6.x and 0.5.x in place; your data, NFs, accounts and license are kept. *SYSTEM > About > Software updates* offers this version.
Linux x86_64: `kaldrivon-minismo_0.7.1-1_amd64.deb` and `kaldrivon-minismo-0.7.1-1.x86_64.rpm` (checksums in `SHA256SUMS`, signed by Kaldrivon in `SHA256SUMS.sig`; the public key is `kaldrivon-linux-signing.pub`). MiniSMO 0.7.0 on Linux can install this version from the web UI.

## O-Cloud

- O-Cloud performance: the O-Cloud's *Monitoring* tab has the O-Cloud's measurement jobs, retention period, report subscriptions and performance dictionaries (O2ims infrastructure performance). MiniSMO can subscribe to reports, which are shown as received. With changes allowed for the O-Cloud, measurement jobs can be created, changed, suspended, resumed and deleted, and the retention period set; each change is confirmed and in the Audit Log. The Demo Network's O-Cloud offers it with synthetic data.
- O-Cloud NF Deployments can be healed and upgraded (with changes allowed for the O-Cloud, each confirmed and in the Audit Log): **HEAL…** restarts chosen Pods of a Kubernetes workload, or asks an ETSI NFV deployment manager to heal a VNF instance; **CHANGE PACKAGE…** moves a VNF instance to another VNF package. The Demo Network's O-Cloud answers them with synthetic data.
- O-Clouds are treated like NFs on the FCAPS pages: choose an O-Cloud in *FCAPS > Performance* (what it measures and the reports it sent) and in *FCAPS > Software & Hardware > Hardware* (its servers and other resources); its alarms are acknowledged and cleared in the Alarm Console. The O-Cloud page keeps pools and sites, resource types, deployment managers, provisioning and a new *Monitoring* tab (measurement jobs, report subscriptions, retention); its Alarms, Resources and Performance tabs moved to the FCAPS pages (old links still work).
- FCAPS > Performance for an O-Cloud now has charts: CPU and memory of the nodes and workloads of a Kubernetes deployment manager (its resource metrics API), and the values of the VNF performance reports of an ETSI NFV deployment manager. The demo O-Cloud offers both.

## RAN functions, A1, R1 and intents

- A1-ML model training for Near-RT RICs: a Near-RT RIC can ask which training environments MiniSMO offers, create an AI/ML model training job, read its status, be told of its changes and cancel it, over the northbound listener with an API token. Training is done by you: *TOOLS > Northbound > A1-ML Training* lists the jobs and marks them running, succeeded (with the trained model's location) or failed; each change is confirmed and in the Audit Log.
- AI/ML model training on a Near-RT RIC: the A1 Policies tab of a Near-RT RIC shows the training capabilities it offers and can ask it to train a model (with the new write class *A1 AI/ML model training*). The RIC reports the job's status to MiniSMO, shown as received; jobs can be read again and cancelled. The Demo Network's RIC offers it with synthetic data.
- R1: rApps can now offer the data they produce by pull (MiniSMO fetches it from the rApp when told it is ready) or by Kafka (the rApp writes to a topic on the Kafka bus set in *Settings > Operations*, new setting *Kafka bus for R1 data offers*). Subscribers to an rApp's data can use push, pull or Kafka.
- NFs can have a site location (latitude and longitude, in **CHANGE…** on the NF). Intents can now name an area (a polygon): only NFs whose site is inside it are covered. Intent throughput targets can be limited to UE groups (a 5QI or a network slice), checked from the per-5QI and per-slice throughput measurements.
- Acting on intents: a new automation trigger *INTENT_NOT_FULFILLED* runs a rule when an intent target is checked and missed (optionally for one intent and one target), once for each NF the intent covers; a configuration change it proposes waits for an approval. The intent's report names the rules that act on it.
- Analytics (MDA) reports can be delivered as files: with `reportingMethod` FILE each report is written to a file, announced to the request's reporting target with notifyFileReady and listed by the file data reporting service (file data type Analytics).
- Analytics (MDA): a request can cover an area (the NFs whose site location is inside it) instead of a list of DNs, and can ask for recommended actions: for NFs with high or low PRB usage, a recommendation in words to increase or decrease their radio resources. A recommendation filter (DNs or an area) leaves NFs out of the recommendations.
- A1 policies: a Near-RT RIC can now report a policy's status change to MiniSMO at once (A1 policy status notifications). MiniSMO gives the RIC its notification address with each policy it creates or changes while the northbound listener is on.
- A1 enrichment information: a Near-RT RIC's EI job with a status notification address is told when the job is disabled (MiniSMO stops delivering) or enabled again.
- A1 mutual TLS: the A1 address of a Near-RT RIC can now carry MiniSMO's client certificate and key for a RIC that asks for it (the key is stored protected). It is used for A1 policies and A1 AI/ML model training.
- Intents for a radio service: an expectation of type *Radio_Service* names an area and a service type (SST) and sets per-UE throughput and RAN latency targets, checked from the per-slice throughput and delay measurements of the NFs in the area.
- Analytics (MDA) requests can set thresholds: only NFs whose PRB usage reached or crossed the threshold are reported (up, down, or both with hysteresis), and an output can be given a time after which it is no longer produced.
- Intent coverage targets: *WeakRSRPRatio* and *LowSINRRatio* are now checked from the NFs' RSRP and SINR report distributions (a cell counts when at least half of its reports are below the threshold).

## Fault and performance management

- Alarm *PM file server not trusted*: while a file server of an NF presents an SSH host key or certificate nobody has confirmed, the NF has a MINOR internal alarm naming the servers and where to confirm them (*NETWORK > Network Functions > NF > Monitoring > File-based PM > TRUST…*). It clears when every such server is trusted or forgotten. A server waiting for confirmation can now also be forgotten (**FORGET…**).
- PerfMetricJobs: an NF that lists _3gpp-common-measurements as an import-only module in its YANG library (RFC 8525), as the module only provides groupings used under ManagedElement, is now recognised as supporting PerfMetricJobs; before, MiniSMO said the NF did not announce the model.
- *PM intervals missing* is no longer raised for series MiniSMO stopped reading because the NF now sends the same measurements by itself (for example an O-RU's first read before its reports start).

## Demo Network

- Demo Network: DEMO-OCLOUD now sends performance reports as the report subscription asks (at its report interval, or after each collection of the measurement jobs it covers) instead of every one to two minutes; a report interval shorter than 60 seconds is refused.
- Demo Network: DEMO-O-RU now reports O-RAN performance measurements (receive-window counts and RX power), which appear in *FCAPS > Performance*; they follow the time of day like the rest of the demo.
- Demo Network: MiniSMO now subscribes to DEMO-OCLOUD's server measurements by itself, so *FCAPS > Performance* shows the O-Cloud's reports straight away.
- Demo Network: two demo parties now use MiniSMO's northbound APIs like outside systems: DEMO-RAPP (R1: onboarding, discovery, an R1 data job for alarm events) and DEMO-NEAR-RT-RIC (an A1-EI job for alarm events, the A1-ML training capabilities and, when one is offered, a training request). *SIMULATION > Demo Network* shows what each did and received.
- Demo Network: the lab NFs now send syslog to the destination you set on them (*SET SYSLOG DESTINATION…*, over TLS or UDP), so *LOG > Syslog* can be tried without equipment.
- Demo Network: the cloud-hosted lab NFs are now one NF of each type, DEMO-O-CU-CP, DEMO-O-CU-UP, DEMO-O-DU and DEMO-O-RU. The O-CU-CP, O-CU-UP and O-DU are managed as 3GPP NFs: you can set MiniSMO as their VES destination and create PM jobs on them, and they then report their measurements, alarms and heartbeats. The earlier DEMO-LAB-CU-1, DEMO-LAB-DU-1, DEMO-LAB-RU-1 and DEMO-LAB-NTS-DU are replaced by the new ones when MiniSMO starts.
- Demo Network: it is now the demo O-Cloud and its four demo NFs only; the 8 simulated NFs (DEMO-O-CU-CP-001 ... DEMO-O-RU-004) are no longer created and are removed from existing installations when MiniSMO starts. Scenarios, test alarms (RAISE TEST ALARM…) and the alarm activity setting act on the demo NFs, through their devices: a cell really goes out of service, a connection really drops, and the alarms arrive as the NFs' own notifications.
- Demo Network: MiniSMO sets itself as the VES destination of DEMO-O-CU-CP, DEMO-O-CU-UP and DEMO-O-DU and creates one PM job on each when the Demo Network starts, so their measurements appear in *FCAPS > Performance* without set-up.
- Demo Network: DEMO-O-RU supports VES as O-RAN WG4 defines it (a configured subscription to MiniSMO's collector and supervision heartbeats, set by MiniSMO when the Demo Network starts) and reports its alarms in its O-RAN alarm list as well.
- Demo Network: DEMO-O-RU now connects by NETCONF Call Home (it calls MiniSMO, as O-RAN radio units do), and DEMO-O-CU-UP by NETCONF over TLS with Call Home over TLS, so both can be tried without equipment. It is listed under *SYSTEM > Settings > NETCONF Call Home* like any calling NF. With Call Home switched off, MiniSMO connects to it as before.
- Demo Network: after MiniSMO restarts, the demo NFs get their VES destination again even when they connect before the VES collector is listening, so no *VES heartbeat missed* alarms appear. The 3GPP demo NFs report a dnPrefix, so their ManagedElement IDs no longer count as an identity conflict.
- The Network Functions list shows the Demo Network's NFs with origin *Demo Network*, and Topology marks them DEMO.
- Demo Network: the demo NFs answer `get-schema` for every module they announce and no longer announce modules they do not implement, so reading their YANG no longer leaves errors in the NETCONF Log.
- Deleting the Demo Network now removes all of it: the demo rApp offboards and deletes its data job, the demo RIC deletes its A1-EI and training jobs, and the demo NFs' log entries, the demo O-Cloud's alarms and its certificate are removed too.

## Working with MiniSMO

- Deleting an NF now also removes its configuration search index, YANG module list, baseline, accepted deviations, cell states and A1-ML client data.
- *Settings > General* no longer shows *Simulated PM update interval*: the Demo Network's NFs report their own measurements, so the setting had no effect.
- Help, Quick Start and User Guide: checked against this version and brought up to date (the Demo Network as NETCONF devices, O-Cloud pages, every write MiniSMO can send, internal alarms, PM retention); *SYSTEM > Settings* now has a complete reference of every General setting with its default and allowed values, and the screenshots show the current pages.
- License agreement version 1.1: it now says plainly that you may replace an open-source component with a modified version where its license (such as Paramiko's LGPL-2.1) allows it. The third-party notices are completed and list what the Linux packages contain.
